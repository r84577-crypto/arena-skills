# قاعدة البيانات — التشغيل والاستعادة (DR)

الحقيقة أولاً: القاعدة الحية تحوي كائنات من ثلاث مراحل، والمستودع
يغطيها جزئياً. هذا الملف يوثّق الواقع كما هو، لا كما يُتمنى.

## ما هو موثّق في المستودع

| الملف | يغطي |
| --- | --- |
| `db/migrations/2026*.sql` (faw_*) | مخططات الذاكرة والملف الشخصي (المرحلة 1) |
| `db/migrations/20261111000000_*_rls.sql` | عزل `personal_private.secret_notes` |
| `db/migrations/20261111000001_comms_ledger_consolidation.sql` | الدفتر + التدقيق + المالكية + التقسية — آمن التكرار |

## ما هو حيّ فقط (غير مستعاد من المستودع وحده)

- جداول الأعمال في `personal` (15) و`training` (8) و`aon_app` (4)
  و`personal_private` (1) — البنية والبيانات معاً.
- `public.isolation_matrix()` وموجّه الصلاحيات `resolve_scope`.
- مستخدمو `auth` (حساب المالك) وإعدادات المشروع.

## النسخ الاحتياطي (الخطة المجانية)

- Supabase يأخذ نسخاً يومية تلقائياً (الاحتفاظ محدود في المجانية).
- نسخة يدوية قبل أي تغيير هيكلي — من لوحة Supabase ← Database ←
  Backups، أو سطر الأوامر.
- تُحفظ النسخ خارج المستودع (تخزين المالك الخاص) — لا تُدمَج في Git أبداً.

```shell
pg_dump "$SUPABASE_DB_URL" -Fc -f backup-$(date +%F).dump
```

## ترتيب الاستعادة من الصفر

1. مشروع Supabase جديد + استعادة النسخة اليومية (الطريق المفضل).
2. إن تعذّرت النسخة: طبّق هجرات `db/migrations` بالترتيب الزمني، ثم
   أعد بناء جداول الأعمال من تصدير `pg_dump --schema-only` يؤخذ الآن
   ويُحفظ مع النسخ (بند متابعة، غير منجَز بعد).
3. تحقق بعد الاستعادة باستعلامات التحقق أدناه.

```sql
select public.security_sweep()->>'verdict';  -- يجب: clean
select count(*) from public.comms_log;        -- يطابق التوقع
```

## RPO/RTO واقعيان (مجاني)

- فقدان محتمل حتى 24 ساعة (فاصل النسخ اليومية).
- الاستعادة من النسخة: أقل من ساعة عمل مالك واحد.
